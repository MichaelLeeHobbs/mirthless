## Provisional verdicts (pre-acceptance)

**Provisional.** These are not verdicts on the contract. The owner asked for a pass over the P1 rows of Authentication and Connectors while every row is still Proposed, to see where the code stands and whether the rows can be verified at all. Rows the debate replaced, or that are recommended Reject, were skipped in favour of their replacements. When a row is accepted it must be verified again and its verdict moved to the table above; whatever is not accepted is deleted from here. The column is headed "Proposed ID" so that neither the format check nor the coverage script counts these as verdicts.

Verified by five fresh-context verifiers who built none of the code, on the code of revision 29a13266 (docs-only commits since), with the project's own tests run by them, probes against the built packages, and real PostgreSQL, MySQL, Kafka, RabbitMQ, SFTP and mail servers. No Playwright suite and no browser check was run. No test cites a requirement ID yet, so every test named here is also a rename. `itest` means an integration test run against a real service.

### Notes on the requirements

Problems the verifiers found in the wording. Nothing was edited: each is a suggestion for the `srs` skill once you have decided on the row.

- AUTH-USR-02: Does not say whether names that differ only in letter case are the same (both were accepted as new). Suggest: "...refuse to give either, compared without regard to letter case, to another account".
- AUTH-USR-08: As written it also refuses renewing the session, which works today (probe) and the console needs. Suggest "except signing out, renewing the session and changing the password".
- AUTH-LOG-08: "Failed" is unclear for a malformed request (400, counted today). Suggest: "a number of attempts ... were refused for their credentials or form".
- AUTH-SES-08: Two behaviours in one row: the timeout, and what counts as user action. Suggest splitting.
- AUTH-SES-11: "Its session ends" should say on the server, and whether a background tab counts. Suggest: "within 60 seconds after its session ends on the server, or on the tab's next display if it is hidden".
- AUTH-MFA-02: Five conditions in one row (active only after a code, encrypted, no other service, never shown again). Suggest splitting the secret's protection from enrolment.
- AUTH-KEY-05: "In its URL" does not say whether the path and public routes count. Suggest: "...a request to any route that needs sign-in whose URL (path or query, encoded or not) carries an API key...".
- AUTH-KEY-10: A key cannot be issued past its issuer's access, and shortening that access disables the key, so "lost only by the passing of time" has no ordinary path. Suggest: "given back at least until the key's end", and say what a shorter return does.
- AUTH-CUT-09: "Revoked" has no subject here, and nothing says how a test sees that sending stopped. Suggest: "...within 60 seconds after its caller's session or API key stops being accepted, close the connection of an answer still being sent."
- AUTH-CUT-13: Does not say what a person who may disable users but not read keys sees. Suggest naming the keys for anyone who may disable the user.
- CONN-SRC-03: Add "except as CONN-DCM-12 says for DICOM" (the sender was answered at C-STORE). Compound: refusal, retaking and crash are three behaviours; consider three rows.
- CONN-SRC-04: Only a server stop is excused; a channel halt between recording and settling behaves the same for brokers. Either excuse a halt too or keep it as a defect. Also say what a lost commit (broker refuses the commit) counts as.
- CONN-SRC-05: Say whether header, key and source-map text counts as "a message in which bytes ... were replaced".
- CONN-SRC-10: Say whether a port a listening source cannot bind is "cannot reach its partner". Compound: log, alert and retry could be three rows.
- CONN-SRC-13: "Take no new message" should say whether a frame or request already received but not yet recorded is new. Compound: taking and answering are two behaviours.
- CONN-SRC-14: Compound: the setting, and its import default, are two rows (the second is MIG). Say which source types the setting must exist on.
- CONN-SRC-15: Add the DICOM exception (CONN-DCM-12 answers at storage). Compound: answering and leaving the input are two behaviours.
- CONN-DST-05: Say which settings "decide where the message goes" (HTTP query parameters? SMTP cc and bcc? KAFKA key?), so a test can list them.
- CONN-DST-09: List the partial acceptances meant (SMTP recipients, FHIR batch entries, DICOM instances), or the row cannot be tested to completion.
- CONN-DST-10: Say what an SMTP acceptance is when some recipients are refused, or point at CONN-DST-09.
- CONN-DST-12: Say whether FILE, CHANNEL and JAVASCRIPT need a setting of their own, and what DICOM counts as one send (its limit is per step, with retries).
- CONN-CFG-02: Say whether a HEAD or a metadata GET is allowed ("send no message" does not say it).
- CONN-TCP-03: Two behaviours in one row, and silent on a message without MSH-10. Suggest: "... and whose MSA-2 is empty, equals the MSH-10 it sent or that field's first component, or is anything when it sent no MSH-10", and a separate row for what an error records. Say whether lower case counts.
- CONN-TCP-04: D-253 allows an empty start and forbids an empty end; the row's "of any length" does not say so.
- CONN-TCP-11: Say how a test tells "vanished": no packet answered, as opposed to idle but alive, which CONN-TCP-10 keeps open.
